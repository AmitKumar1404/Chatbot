FIX/MULTI-USER-LOGIN — INTERVIEW PREPARATION
Evidence: fix-owned commit ba1f78a; corresponding docs, diff, and current source at a62003a.
Scope note: Actual code change only AuthContext token reads/writes/removes from localStorage to sessionStorage. Search-dialog commit 51ad3cc is inherited ancestry. No automated multi-tab test.

PROJECT CONTEXT
===============
Q1. Bug kya tha?
Answer:
localStorage origin-wide shared tha, so same browser ke separate tabs ek access token share karte the. User A and User B ko independent tabs me login karna expected tha, but token overwrite/logout cross-tab identity mix-up create kar sakta tha.

Q2. Fix kya tha?
Answer:
Same token key ke AuthContext bootstrap, login set, invalid-token cleanup and logout remove operations sessionStorage par switch kiye. Backend/API/DB unchanged.

SECTION 1 — BASIC INTERVIEW QUESTIONS
===============
Q3. localStorage vs sessionStorage?
Answer:
localStorage same origin tabs/windows me shared and persistent hota hai. sessionStorage tab browsing context scoped hota hai and tab session close tak रहता है, though duplicated-tab behavior browser-dependent/copy-like ho sakta hai.

Q4. Kya sessionStorage secure hai?
Answer:
It improves isolation, confidentiality against XSS nahi. JavaScript-readable token malicious injected script read kar sakta hai.

SECTION 2 — PROJECT-SPECIFIC INTERVIEW QUESTIONS
==========================
Q5. Kaun sa file changed?
Answer:
frontend/src/context/AuthContext.jsx only. ba1f78a me five localStorage calls equivalent sessionStorage calls me swapped hue.

Q6. Auth bootstrap kaise work karta hai?
Answer:
Provider tab storage se token read karta hai, auth state initialize/validate flow chalata hai, login par token store karta hai, and logout/invalid path par same tab key remove karta hai.

SECTION 3 — WHY / WHY NOT QUESTIONS
=====================
Q7. Key ko username se namespace kyun nahi?
Answer:
One tab me one current identity model ke liye tab-scoped single key simpler hai. localStorage username namespace still active-current-user coordination and token exposure create karta.

Q8. HttpOnly cookie kyun nahi in this fix?
Answer:
That needs backend cookie issuance, CSRF strategy, CORS/SameSite/refresh changes. ba1f78a targeted minimal frontend tab-isolation fix. HttpOnly cookie stronger XSS token-theft mitigation follow-up hai.

Q9. In-memory only token kyun nahi?
Answer:
More XSS-resilient persistence profile but refresh loses login unless refresh cookie/backend flow. sessionStorage balances tab refresh persistence and tab isolation.

SECTION 4 — HOW DOES IT WORK?
==========================
Q10. Two-tab scenario trace?
Answer:
Tab A sessionStorage token A stores; Tab B has separate storage and token B stores. Each AuthContext API/STOMP calls apna token use karte hain. Tab A logout only A key remove karta hai.

Q11. Page refresh?
Answer:
Same tab sessionStorage survives refresh, so provider token restore kar sakta hai. Tab/window close par session ends and token normally removed by browser.

SECTION 5 — FOLLOW-UP QUESTIONS
===================
Q12. Follow-up: duplicated tab?
Answer:
Some browsers duplicated tab ko initial sessionStorage copy de sakte hain; after duplication storage contexts independent ho sakte hain. Therefore “always blank new tab” guarantee nahi.

Follow-up Q12.1. New tab opened with window.open?
Answer:
Opener/session behavior browser rules par depend kar sakta hai. Sensitive isolation requirement automated browser tests se verify karunga and noopener policy consider karunga.

Q13. Follow-up: token expires?
Answer:
sessionStorage expiry validate nahi karta. Backend rejects expired JWT; frontend invalid-token path state/key clear kare. Refresh-token behavior later feature hai, ba1f78a ka part nahi.

Q14. Follow-up: logout all tabs?
Answer:
This fix intentionally per-tab logout deta hai. Global logout requirement ho to server revocation plus BroadcastChannel/storage-independent signal needed.

SECTION 6 — WHAT-IF / EDGE CASE QUESTIONS
======================
Q15. User manually token edit kare?
Answer:
Client state trusted authority nahi. Backend signature/expiry validates; invalid token cleanup and login redirect expected.

Q16. Storage unavailable?
Answer:
Browser policy/private mode operation throw kar sakta hai. Graceful unauthenticated fallback needed; current change ko robust storage exception handling guarantee nahi bolunga.

Q17. Tab crash/reopen?
Answer:
sessionStorage usually lost after browsing context closes, so login required unless separate refresh mechanism. This is expected trade-off.

SECTION 7 — ERROR HANDLING & FAILURE SCENARIOS
========================
Q18. Login API success but storage set fail?
Answer:
UI token memory/storage state inconsistent ho sakti hai. Store error catch, auth state rollback, and user feedback stronger handling hai.

Q19. 401 response?
Answer:
Current tab token/auth state clear and redirect/login flow trigger hona chahiye. Another tab's valid session should remain unaffected.

SECTION 8 — SECURITY QUESTIONS
==================
Q20. Threat model improvement?
Answer:
Accidental cross-tab user identity sharing reduce. XSS, token replay, compromised browser extension, and server revocation problems remain.

Q21. Stronger auth storage?
Answer:
Short-lived access token in memory plus Secure HttpOnly SameSite refresh cookie, CSRF controls, refresh rotation/revocation, CSP and dependency hygiene.

Q22. Token logging?
Answer:
Never console/server logs me raw JWT. Storage change secrets-handling discipline replace nahi karta.

SECTION 11 — FRONTEND QUESTIONS
===================
Q26. AuthContext centralization benefit?
Answer:

SECTION 12 — CONCURRENCY / REAL-TIME QUESTIONS
================================
Q28. WebSocket effect?
Answer:

Q29. Race: logout while request pending?
Answer:
Pending request old token carry kar sakti hai. Abort requests/socket disconnect on logout and ignore stale response by auth generation ID.
