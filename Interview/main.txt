Q8. StreamDownstreamEvent kyun?
Answer: Yeh `chunk`, `done`, aur `error` frames ko typed envelope deta hai. `type` event kind batata hai aur normal correlated events me `clientStreamId` stream identify karta hai. Baaki fields event-dependent/optional hain:

* `assistantMessageId` chunk/error aur many DONE flows me bubble route karta hai, lekin har frame me guaranteed nahi.
* `chunk` sirf chunk event ke text ke liye hai.
* `message` error event ke liye hai.
* `chatSessionId` `sendJsonToUser` ke terminal/session-sync paths me set ho sakta hai; ordinary chunks me present nahi hota.

STOP ka DONE event current handler me sirf `clientStreamId` ke saath ban sakta hai, isliye optional fields ko universal nahi kehna chahiye.

Q9. ChatServiceImpl role?
Answer: Owner-scoped session CRUD/history, synchronous chat path, stream begin/partial/final persistence, edit target resolution, feedback-enriched message DTO aur title refresh.

Q10. ActiveStreamRegistry role?
Answer: Per-principal local Disposable manage, atomic compute se replace/cancel, Redis metadata mirror/read, duplicate client stream detect, disconnect markers aur stale callback matching.

Q11. RedisInfraStateStore role?
Answer: Active stream JSON TTL keys, disconnected-user sorted set aur rate-limit counter helper manage karta hai. Active-stream aur disconnected-marker operations ke liye per-instance `ConcurrentMap` fallback hai. Rate-limit counter ka in-memory map fallback nahi hai; Redis unavailable ho to helper `1` return karta hai.

Q12. Frontend ChatApp role?
Answer: Sessions/messages, STOMP lifecycle, client stream correlation, recovery, edit/stop, search navigation, pin, feedback, documents/mode aur voice-adjacent orchestration.

Q13. Auth architecture?

Q14. RAG architecture?

SECTION 3 — WHY / WHY NOT QUESTIONS
=====================
Q15. STOMP simple broker kyun?
Answer: Spring-native setup aur per-user destinations simple. Multi-node durable messaging/replay ke liye external broker needed; current simple broker process-local.

Q16. Partial response persist kyun?
Answer: Reconnect/history me generated content recover ho sake. Frequent writes load badhate; throttling/coalescing trade-off.

Q17. clientStreamId aur server streamId dono kyun?
Answer: Client ID UI/retry correlation, server ID active execution identity/stale callback guard. One ID reuse trust/race boundaries mix karta.

Q18. Short transactions streaming me kyun?
Answer: Long Ollama stream ke across DB transaction/connection hold avoid hota. Trade-off intermediate incomplete state explicitly manage karna.

Q19. Redis fallback kyun?
Answer: Redis outage me single-instance functionality degrade gracefully. Multi-instance consistency fallback me break ho sakti; availability vs consistency trade-off.

Q20. JWT stateless kyun?
Answer: REST scaling/simple auth. Immediate access-token revocation difficult; refresh token DB rotation separate control hai.

Q21. sessionStorage over localStorage kyun?
Answer: fix/multi-user-login ne tabs ko independent login identity di. Refresh/restart persistence lower; both JS-readable and XSS-exposed.

Q22. Refresh token hash kyun?
Answer: DB leak me raw long-lived bearer token expose na ho. Rotation replay window still concurrency controls maangti.

Q23. Flyway kyun?
Answer: V1-V12 deterministic schema evolution/deployment reproducibility. Entity auto-ddl production migration substitute nahi.

Q24. Optimistic feedback/pin UI kyun?
Answer: Perceived latency low. Rollback/order handling required; feedback has rollback, all flows equal guarantees nahi.

SECTION 6 — WHAT-IF / EDGE CASE QUESTIONS
======================
Q45. Redis down?
Answer: Store logs warning once-ish and local maps fallback. Single node continues; multi-node metadata divergence possible.

Q46. Ollama down mid-stream?
Answer: `ChatWebSocketController.doOnError` pehle `isTransientStreamingFailure(e)` check karta hai.

* Connection refused, timeout, premature close jaise transient failures par controller error event, DONE event, aur `persistOnce()` emit/call nahi karta. `doFinally` active stream metadata cleanup karta hai; pehle se throttled partial DB state ho sakti hai.
* Non-transient failure par error text accumulator me append hota hai, persistence run hoti hai, phir correlated ERROR aur DONE events bheje jate hain.

Automatic retry/circuit breaker ka evidence nahi hai.

Q47. DB down mid-stream?
Answer: Partial/final persistence fail; client may have chunks not durable. Transaction only individual DB operation cover karta.

Q48. Browser disconnect briefly?
Answer: Grace marker avoids immediate cancel; reconnect recovery status/history reconcile. Grace expiry cleanup cancels local stream when execution owner reachable.

Q49. Two tabs same user?
Answer: Auth can be tab-specific users via sessionStorage, but same principal active registry keyed username means one active stream can replace another; client IDs reduce UI confusion, not independent per-tab streams.

Q50. Duplicate chat publish?
Answer: Same clientStreamId active ho to duplicate guard. After completion/retry durable idempotency key uniqueness evidence N/A.

Q51. Concurrent refresh?
Answer: Explicit row lock/conditional revoke evidence absent; both may observe valid token. Atomic consume/token family replay detection improvement.

Q52. Search result deleted before click?
Answer: Navigation/history fetch can fail/miss; frontend should stale result handle. Dedicated test absent.

Q53. Concurrent feedback first insert?
Answer: V7 unique prevents duplicate, one request constraint fail possible.

Q54. Same PDF concurrent upload?
Answer: Global V12 unique final guard, but orphan file/partial work possible.

Q55. RAG prompt injection?
Answer: Delimiter/instruction reduces risk, not guarantee. Document untrusted input.

Q56. Speech API unsupported?
Answer: Mic disabled; typing works.

SECTION 7 — ERROR HANDLING & FAILURE SCENARIOS
========================
Q57. GlobalExceptionHandler mappings?
Answer: BadCredentials→401, UsernameNotFound→404, RuntimeException→400, generic→500. Domain precision coarse; tip-only feedback unreadable handler main me absent.

Q58. REST vs STOMP errors?
Answer: REST status/ErrorResponse; stream path correlated error event. Client must stop pending state on terminal event.

Q59. Transient streaming failures?
Answer: StreamConstants classifier/reconnect UI handles selected cases; exact automatic retry semantics should not be overstated.

Q60. Partial data compensation?
Answer: DB transactions rollback DB scope only. Filesystem, email, Ollama/browser side effects need explicit compensation; document upload lacks it.

Q61. Rate limit rejection?
Answer: Bucket4j IP filter login/chat routes configuration based. Distributed consistency uncertain because filter buckets may process-local; Redis counter helper structure is not proof of wired distributed limiting.

Q62. Password reset email fail?
Answer: `MailServiceImpl.sendPasswordResetEmail` `mailSender.send(...)` ke around every `Exception` catch karke sirf error log karta hai; exception caller ko rethrow nahi hoti. Isliye `requestReset()` generic success return kar sakta hai aur reset token transaction commit ho sakta hai even when email delivery fail hui. Retry ya outbox implement nahi hai.

Production improvement:
Durable outbox/job, retry policy, delivery metrics, aur user-enumeration-safe response retain karke operational failure track karo.

Q63. Better error model?
Answer: Domain exceptions with stable codes: 400 validation, 401 unauth, 403 ownership, 404 missing, 409 state/conflict, 429 limit, 503 dependencies.
