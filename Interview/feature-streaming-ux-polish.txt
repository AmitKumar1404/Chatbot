SECTION 1 — BASIC INTERVIEW QUESTIONS
===============
Q3. sessionStorage kya advantage deta hai?
Answer:
State tab-scoped hoti hai and tab session tak survive karti hai. localStorage jaisa all-tabs sharing nahi, so same username ke parallel tabs me ownership mix-up reduce hota hai.

Q4. Heartbeat ka role?
Answer:
Transport liveness detect karne me help karta hai. Heartbeat missed hone par disconnect lifecycle trigger ho sakti hai; heartbeat application message replay guarantee nahi karta.

SECTION 2 — PROJECT-SPECIFIC INTERVIEW QUESTIONS
==========================
Q5. Ownership record me kya correlate hota hai?
Answer:
clientStreamId, assistantMessageId, sessionId and username/tab context. UI incomplete assistant row tabhi allow karti hai when persisted/current data owned record se match kare.

Q6. StreamingMessageRenderer current status?
Answer:
f3fb373 ne component add kiya for incremental rendering/animation, but current main usage search me import/caller nahi. Interview me “file implemented” bolunga, “current production renderer” nahi; later ChatWindow ReactMarkdown path live hai.

SECTION 3 — WHY / WHY NOT QUESTIONS
=====================
Q7. Username alone ownership kyun insufficient?
Answer:
Same authenticated user multiple tabs me different chats/streams चला सकता hai. Principal identity authorization deta hai, UI operation ownership nahi.

Q8. localStorage kyun nahi?
Answer:
localStorage same origin ke tabs share karte hain, so one tab another tab ka stream owner dikh sakta hai. sessionStorage isolation desired behavior se align karta hai.

Q9. window unload par backend stream cancel kyun nahi always?
Answer:
Unload unreliable hai and reconnect recovery may intentionally let generation continue. Cleanup should local socket/state hygiene and backend disconnect grace semantics distinguish kare.

SECTION 4 — HOW DOES IT WORK?
==========================
Q10. Stream start se completion flow?
Answer:
1. Start par `f3fb373` tab ownership metadata sessionStorage me save karta hai.
2. Inherited event handler current `clientStreamId` aur optional assistant-message identity check karta hai.
3. Later `activeConnectionId` logic stale WebSocket connection callbacks isolate karta hai; yeh `f3fb373`-owned change nahi hai.
4. DB reconciliation incomplete row ko matching owned tab ke liye hi streaming dikhati hai.
5. Done/cancel/terminal cleanup ownership clear karta hai.

Q11. Disconnect cleanup?
Answer:
Backend session listener disconnected timestamp mark karta hai; reconnect onSessionConnect marker clear kar sakta hai. Scheduled cleanup grace period cross karne wale disconnected principals ke active work ko cancel karta hai.

Q12. Incomplete assistant filtering kyun?
Answer:
Without filter, same user ka another tab persisted generationComplete=false row local active stream bubble ban sakta tha. allowIncompleteAssistant ownership predicate accidental cross-tab rendering reduce karta hai.

SECTION 5 — FOLLOW-UP QUESTIONS
===================
Q13. Follow-up: sessionStorage write fail?
Answer:
Code private mode/storage failures catch/ignore karta hai. Safe behavior should be conservative: unproven incomplete stream render/claim na ho, while completed persisted messages still show.

Follow-up Q13.1. Tab duplicate karne par?
Answer:
Browser duplicate semantics storage copy kar sakti hain, so perfect unique tab identity assume nahi karna. Add explicit random tabId and lease/heartbeat for stronger ownership.

Q14. Follow-up: heartbeat scheduler dedicated kyun?
Answer:
Broker heartbeat tasks ko predictable scheduler chahiye. Scheduler sizing/daemon lifecycle production config concern hai; heartbeat alone distributed execution coordination nahi.

Q15. Follow-up: stale done event?
Answer:
DONE event ka `clientStreamId` current active client stream se match hona chahiye. Agar event me `assistantMessageId` present hai aur current expected assistant ID bhi known hai, dono bhi match hone chahiye. DONE handler session ID compare nahi karta. Stale WebSocket connection callbacks ka separate `activeConnectionId` isolation later `c291a9f` behavior hai.

SECTION 6 — WHAT-IF / EDGE CASE QUESTIONS
======================
Q16. Same user, same chat, two tabs?
Answer:
sessionStorage record each tab ko local owner context deta hai, but backend principal-wide active key may serialize/replace streams. Exact product policy explicit honi chahiye: one active stream per user versus per tab/session.

Q17. Page refresh during stream?
Answer:
sessionStorage survives refresh in same tab, enabling recovery correlation. Current active endpoint/DB partial rows inherited reconnect behavior provide authoritative reconciliation.

Q18. Partial Markdown fence mid-stream?
Answer:
Incremental parser temporarily incomplete syntax dekh sakta hai. Renderer should tolerate incomplete fences and avoid unsafe raw HTML. Current dead renderer path ko active guarantee nahi bolunga.
