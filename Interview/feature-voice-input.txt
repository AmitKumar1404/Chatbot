INTERVIEW PREPARATION
Branch: feature/voice-input

PROJECT CONTEXT
===============
Purpose: Normal/document mode regression restore karna aur browser Web Speech API se voice-to-text input dena.
Evidence: `920edf5` explicit NORMAL/DOCUMENT routing restore karta hai; `5df9a34` InputBox me voice input add karta hai. Main PR #35/#36 se dono commits contain karta hai.
Key boundary: Backend audio endpoint, audio persistence aur server-side speech model N/A. Final browser transcript ordinary text ban kar existing STOMP chat flow use karta hai.
Privacy caveat: Application backend audio upload nahi karta, lekin browser/vendor implementation remote recognition service use kar sakti hai. “Audio device se kabhi bahar nahi jata” repository se prove nahi hota.
Test evidence: Main me voice-specific ya mode-regression automated tests nahi mile.

SECTION 1 — BASIC INTERVIEW QUESTIONS
===============
Q1. Voice input feature ko simple words me explain karo.
Answer: User mic button se browser `SpeechRecognition` start karta hai. Sirf final recognized text textarea me append hota hai; user usse edit karke normal Send/Enter flow se bhejta hai. Yeh speech-to-text progressive enhancement hai, speech-to-speech feature nahi.

Follow-up Q1.1. Unsupported browser me core chat fail hoga?
Answer: Nahi. Mic disabled rehta hai aur explanatory title dikhta hai; typed input fully available rehta hai.

Q2. Is branch ki exact lineage kya hai?
Answer: `920edf5` pehle normal/document chat separation restore karta hai. Uske baad `5df9a34` browser voice input add karta hai. Voice implementation ka backend audio se koi contract nahi.

Q3. SpeechRecognition kaise detect aur configure hota hai?
Answer: SSR-safe `typeof window !== "undefined"` guard ke baad `window.SpeechRecognition || window.webkitSpeechRecognition` use hota hai. `lang = navigator.language || "en-US"`, `continuous = true`, aur `interimResults = false` set hote hain.

SECTION 2 — PROJECT-SPECIFIC INTERVIEW QUESTIONS
==========================
Q4. `getRecognition()` ka project-specific flow kya hai?
Answer:
1. Unsupported environment me `null` return.
2. `recognitionRef.current` ho to same instance reuse.
3. Standard ya webkit constructor se instance create.
4. Language, continuous aur interim settings configure.
5. `onstart`, `onresult`, `onerror`, `onend` callbacks register.
6. Instance ref me cache karke return.

Follow-up Q4.1. React state ke bajay ref kyun?
Answer: Recognition ek imperative mutable browser object hai. Ref renders ke across same instance rakhta hai bina unnecessary rerender ke; UI-facing text/listening/error state React state me rehti hai.

Q5. `onresult` transcript ko kaise process karta hai?
Answer: `event.resultIndex` se results iterate hote hain, only `isFinal` results combine hote hain, blank final ignore hota hai. Functional `setText` latest typed text preserve karke required space ke saath transcript end me append karta, error clear karta aur textarea focus karta hai. Caret-position insertion aur duplicate-final dedupe implemented nahi.

Q6. Mic start/stop aur component lifecycle kaise coordinate hote hain?
Answer: `handleMicClick` unsupported/disabled/streaming guard karta, listening ho to stop karta, warna recognition start karta hai. `stopRecognition` ref absent ho to no-op, `stop()` ko try/catch karta aur listening false karta hai. Send, response Stop, disabled/streaming effect aur unmount cleanup recognition stop karte hain; unmount par ref null hota hai.

SECTION 3 — WHY / WHY NOT QUESTIONS
=====================
Q7. Browser Web Speech API kyun choose ki, backend STT kyun nahi?
Answer: Browser API se low implementation cost, no app-server audio upload/storage aur existing text pipeline reuse milta hai. Trade-off browser support, vendor behavior, privacy variability aur limited control hai. Consistent cross-browser/custom-model/compliance requirement aaye to backend STT consider hoga.

Follow-up Q7.1. Backend STT add karne par kya naya design chahiye?
Answer: Audio capture/streaming contract, MIME/size/duration limits, consent, authentication, rate limits, storage/retention policy, model capacity, timeout/retry aur sensitive observability.

Q8. `continuous=true` aur `interimResults=false` kyun?
Answer: Continuous mode user ko multiple phrases dictate karne deta hai, although browser session autonomously end kar sakta hai. Final-only results flicker aur partial/final reconciliation avoid karte hain, lekin live partial captions nahi milte.

Q9. Transcript auto-send kyun nahi hota aur streaming ke time mic disabled kyun hai?
Answer: User recognition mistakes review/edit kar sakta hai, accidental send risk kam hota hai. Existing assistant stream ke during mic stop/disable karke competing lifecycle/input states simplify kiye gaye hain; draft dictation during streaming current requirement nahi.

SECTION 4 — HOW DOES IT WORK?
==========================
Q10. End-to-end numbered flow trace karo.
Answer:
1. InputBox browser support detect karta hai.
2. User mic click karta hai; browser permission/recognition start hota hai.
3. `onstart` error clear aur listening state true karta hai.
4. `onresult` only final transcript textarea me append karta hai.
5. User transcript edit/confirm karta hai.
6. Send recognition stop karta aur existing `onSend` call karta hai.
7. ChatApp NORMAL ya DOCUMENT mode fields ke saath ordinary text STOMP payload banata hai.
8. Existing authenticated streaming backend response process karta hai.

Follow-up Q10.1. Permission app manage karti hai?
Answer: Permission browser manage karta hai when recognition starts. App user-initiated click use karti aur denial event ko readable UI error me map karti hai; browser settings change app ke control me nahi.

Q11. Important callback behavior kya hai?
Answer: `onstart` error clear/listening true; `onresult` final text append; `onerror` known browser error ko message me map aur listening false; `aborted` ignore; `onend` listening false. Auto-restart implemented nahi.

Q12. Keyboard, send aur stop behavior?
Answer: Enter without Shift nonblank text send karta, Shift+Enter newline; streaming ke waqt Enter ignored. Send se pehle recognition stop hota hai. Same button streaming state me recognition stop karke existing `onStop` call karta hai.

SECTION 5 — FOLLOW-UP QUESTIONS
===================
Q13. User typing aur speaking ek saath kare to kya hota hai?
Answer: Transcript functional state update use karta hai, isliye callback latest typed text ke end me append karta hai aur stale-closure overwrite risk reduce hota hai. Current caret location preserve nahi hoti; transcript always end me add hota hai.

Follow-up Q13.1. Language aur punctuation control kahan hai?
Answer: Language automatic `navigator.language` hai; manual selector N/A. Punctuation browser transcript par depend karti hai; custom voice commands/parser N/A.

Q14. Recognition khud end ho, silence ho ya network fail ho to?
Answer: `onend` listening false karta. `no-speech`, `network`, permission denial aur missing microphone ke specific messages hain. Typed fallback available rehta hai; automated retry loop nahi.

SECTION 6 — WHAT-IF / EDGE CASE QUESTIONS
======================
Q15. Rapid double click, stream start aur unmount race kaise behave karte hain?
Answer: Rapid duplicate `start()` throw kar sakta hai, jise catch karke generic start error dikhaya jata hai. Stream/disabled effect recognition stop karta hai. Unmount stop + ref null karta hai, lekin listeners explicitly detach nahi hote; late callback risk ko generation token/listener cleanup se stronger banaya ja sakta hai.

Follow-up Q15.1. Explicit state machine kya improve karegi?
Answer: IDLE/STARTING/LISTENING/STOPPING/ERROR states rapid click aur delayed callback ambiguity reduce karengi; current boolean `isListening` browser operation state ko fully represent nahi karta.

Q16. Empty, duplicate ya aborted result ka kya?
Answer: Empty final transcript ignore hota hai. `aborted` error UI message nahi set karta aur `onend` se state clear expected hai. Duplicate final event received ho to text dobara append ho sakta hai; dedupe N/A.

Q17. Multiple tabs aur microphone contention?
Answer: Har tab ka independent component/ref/permission context hai. Browser shared microphone contention decide karta hai. Voice state Redis/DB me shared nahi; sent text ke baad existing per-user stream behavior apply hota hai.

SECTION 7 — ERROR HANDLING & FAILURE SCENARIOS
========================
Q18. Browser errors exactly kaise map hote hain?
Answer: `not-allowed`/`service-not-allowed` → microphone denied; `audio-capture` → no microphone; `no-speech` → no speech; `network` → recognition network error; unknown → generic failure. `aborted` silently ignored. Error `role="status"`/`aria-live="polite"` se announce hota hai.

Follow-up Q18.1. Start ya stop synchronously throw kare to?
Answer: Start failure listening false, visible “could not start” error aur console log deta hai. Stop failure console me log hota hai aur UI listening false ho jati hai; actual browser recognizer state uncertain reh sakti hai.

Q19. Transcript send hone ke baad STOMP/backend fail ho to?
Answer: Voice-specific error path nahi. Transcript ordinary text hai, isliye existing chat STOMP error/reconnect/STOP behavior apply hota hai. Browser recognition errors backend ko send nahi hote.

SECTION 12 — CONCURRENCY / REAL-TIME QUESTIONS
================================
Q30. Voice feature ka main concurrency problem kya hai?
Answer: Browser callbacks, React state/effects, rapid clicks, stream-state changes aur unmount asynchronous order me ho sakte hain. DB transaction voice-recognition stage par relevant nahi.

Q31. Callback idempotency aur stale callbacks?
Answer: Listening false repeatedly set karna harmless hai, but duplicate transcript append idempotent nahi. Ref null listeners detach nahi karta; mounted/generation guard aur handler cleanup stronger design hai.

Q32. Existing real-time system se relation?
Answer: Voice final text ke baad same `clientStreamId`, STOP, reconnect aur correlated stream events use karta hai. Voice audio/listening state Redis ya WebSocket se synchronize nahi hoti.
